# Page templates spec — complete catalog

> Companion to [`welcome-template-spec.md`](welcome-template-spec.md). The welcome is the **directory**; this doc specs every other page in the Storybook + every React component that ships with the templates.
>
> Same data-driven principles: every value the agent fills comes from the manifest, components-index, frontmatter, or live token CSS. Per-team customization happens by editing JSON or one-sentence frontmatter — not by editing MDX.
>
> All glyphs come from the team's icon library (`lucide-react` for shadcn). No emojis.

---

## Enhancement summary  *(deepened 2026-05-09)*

Five parallel research/review agents enhanced this spec. Findings synthesized into **Appendices A–F** at the end of the document. Key insights:

### Confirmed patterns (keep as specced)
- **Carbon-style multi-theme columns** for `<FullSwatchTable>` — rendering all themes simultaneously beats toggle for ≥3 themes. (Appendix B §1)
- **JSON cache + atomic regeneration** for Tracker/Audit (mirrors Istanbul/SonarQube). Live MDX computation rejected — bundle bloat + private-source leak. (Appendix C §2)
- **Static SVG + numbered badges + `<ol>` legend** for `<AnatomyDiagram>` — every reference DS does this. Live overlay-on-component is a maintenance trap. (Appendix B §5)
- **Explicit imports + barrel re-export** in MDX (NOT global `<MDXProvider>` injection — Storybook deprecated that path in 6.1). (Appendix D §1)
- **Pure CSS fill bars** for Tracker/Audit, NOT Recharts (~90KB gzipped for colored rectangles). (Appendix C §6)

### New patterns to adopt (revisions to current spec)
- **`<FullSwatchTable>` paired-foreground sample inside the swatch cell** with live WCAG ratio. Adopt Deliveroo's pattern. (Appendix B §1)
- **Status state machine** with 5 explicit states (`planned | in-development | beta | stable | deprecated | error`) — currently only 4. (Appendix B §6)
- **Sidecar manifest for asset dimensions** generated by `sharp` + `fast-glob`. Don't probe at render time. (Appendix B §4)
- **Anchor freshness to git commit, not wall-clock time** for Tracker/Audit headers. (Appendix C §3)
- **`<Template />` MDX composition pattern** to reduce per-page boilerplate. (Appendix D §1)

### Architectural risks surfaced (Appendix E)
1. **`index-manifest.json` is a god-object** with mixed human/machine ownership → first `evolve` will clobber hand edits.
2. **No JSON Schema for the contracts** → typos break 5+ components silently.
3. **Icon library hardcoded across 10+ components** → swapping libraries means 10+ rewrites.
4. **Mini/Full duplicated chassis** (10 components doing 5 jobs) → drift inevitable.
5. **Tracker computes at render time** → breaks at 500+ component scale.

Top 3 unmitigated risks: **MDX/JSON drift across `evolve` runs** · **Browser-API dependence with no client/server boundary** · **No versioning/upgrade story** for shipped templates.

### Simplicity challenge (Appendix F)
A YAGNI review proposes cutting from 30 components → **6 components (v1 minimum)**, deferring Tracker/Audit/Inventory/Pattern/Data-viz/Spec to v2. Specifically: collapse Mini/Full into a single `<TokenPreview>` chassis; absorb `StatusPill`/`SourceOfTruthList`/`RelatedLinks` into `<PageHeader>`; drop the 7-layer taxonomy. Decision deferred to user — both paths preserved in the spec.

### Recommended pre-flight before any Phase 1 implementation
- Add **Phase 0**: pin JSON schemas (`manifest.schema.json`, `components-index.schema.json`, `frontmatter.schema.json`). Generate TypeScript types from them.
- Decide on the **simplicity scope** (full 30 vs minimal 6).
- Resolve **Open template decision #8** (icon-library adapter) — this couples 10+ components if left.

## Cross-page chrome

Every page (regardless of type) opens with the same chrome — Carbon's pattern:

```
┌─────────────────────────────────────────────────────────────────────┐
│ <H1>                                                                │
│                                                                     │
│ Source · Related · Status pill                                      │  ← link cluster
│                                                                     │
│ <Description from frontmatter — 1 sentence>                         │  ← lede
└─────────────────────────────────────────────────────────────────────┘
```

| Slot | Source | Adaptive? |
|---|---|---|
| H1 | filename → Title Case (override via frontmatter `title`) | adaptive |
| Source link | `manifest.source_of_truth_paths` filtered by current page | adaptive |
| Related links | frontmatter `related: [{ label, href }]` | authored once |
| Status pill | frontmatter `status` | adaptive |
| Description | frontmatter `description` (1 sentence) | authored once |

Component contract — see [§ `<PageHeader>`](#pageheader) below.

> Conceptual content. Explains WHY of the system. Prose-heavy, low live-data.

## Anatomy

```

│ # Principles                                                        │
│ Source code · Related · Status                                      │
│ The three commitments behind shadcn — composition over...           │

## <Section 1>            ← H2 sections (3-6)

optional inline code block

...

| When... | Pick... |

## Source of truth          ← <SourceOfTruthList>

## Related                  ← <RelatedLinks>
```

## Section vocabulary

| Section | What goes there | Required? |
|---|---|---|
| `## Overview` | The shape in 2-4 sentences | Optional (lede may cover it) |
| `## <Topic body>` | 1+ H2 sections | Required |
| `## Decisions` | Team-specific commitments | Recommended |
| `## Do's and don'ts` | Tabular bound rules | Optional |
| `## Source of truth` | Auto-rendered list | Auto |
| `## Related` | Cross-links | Optional |

## Composition over configuration

shadcn names variants for what they do (`destructive`, `ghost`, `link`), not what they look like...

## CSS variables as the contract

Tokens are CSS custom properties on `:root` and `.dark`. Components consume `var(--primary)`, never hex literals...

## Decisions

| When... | Pick... |
|---|---|
| Need a CTA | `<Button>` default variant |
| Need a destructive confirm | `<Button variant="destructive">` |

```

## Section vocabulary (Carbon-style minimum)

- `## <Variant 1>` ... `## <Variant N>` — one H2 per variant in stories file
- `## Sizes` (when applicable)
- `## States` (when applicable)
- `## Accessibility` — bullet list
- `## Theming` — pointer to tokens consumed
- `## API` — auto from `<ArgTypes>`

- `## Related` — optional

## Component contract

```tsx
interface TrackerPageProps {
  manifest: ManifestSchema;
  components: ComponentEntry[];
  pages: Record<string, MdxModule>;  // entire glob
}

  return (
    <div className="hd-tracker">
      <PageHeader frontmatter={{ ...autoFrontmatter, status: undefined }} />
      <FillRatioBar stats={computeOverall(pages)} />
      <FillBySection sections={computeSections(manifest, pages)} />
      <ComponentCoverage components={components} pages={filterByDir(pages, '4-components')} />
      <NextActions ranked={rankNextActions(manifest, components, pages)} />
      <IASyncCheck manifest={manifest} components={components} pages={pages} />
    </div>
  );
}
```

## Data flow — 100% adaptive

| Element | Source |

| Component coverage rows | join of `components-index.json` × `pages['4-components/*.mdx']` |
| Next 5 actions | ranker over `manifest.counts × frontmatter.todos × components.status` |
| IA sync findings | cross-validation between manifest, components-index, pages |

# Open template decisions

1. **Component-page Storybook chrome** — custom `<PageHeader>` (Carbon) vs Storybook's built-in `<Title>` / `<Subtitle>` (Fluent default). Picking custom for v1 simplicity.

2. **`<FullSwatchTable>` theme detection** — auto from manifest vs explicit prop. Leaning auto.

3. **Per-variant captions** — `Story.parameters.docs.description.story` is the canonical Storybook approach. Cap at 1-3 sentences (Fluent pattern).

4. **Theming section auto-derivation** — tokens-consumed list is currently hand-authored. Could derive from a static `tokens-consumed: ['primary', 'ring']` frontmatter field. Defer to v2.

5. **Asset thumbnail strategy** — Vite asset import (live) vs pre-captured screenshots (stable). Picking live; falls back to format-icon for `.fig` / `.sketch` / `.psd`.

6. **Anatomy diagram positioning** — declarative position strings (`top-left` / `middle`) vs explicit pixel coords. Picking declarative for portability.

7. **Tracker / Audit MDX wrapper** — single line `<TrackerPage manifest={...} />` is enough; no need for a richer template. Confirms.

8. **`<FullIconGrid>` for non-React frameworks** — Material's `<md-icon>` is web-component-based; Fluent's `@fluentui/react-icons` is React. The grid component must adapt per icon library. Three implementations needed (or one with adapters).

9. **Stories sort order in component pages** — `Default` always first, then alphabetical? Or follow declaration order in stories file? Picking declaration order (storySort handles it).

10. **Cheat-sheet vs Inventory** — both live in `4-components/`. Inventory is auto, Cheat-sheet is hand. Both render conditionally. Confirms.

# Appendix B · Token visualization deep-dive

Synthesized from cross-DS research (Primer / Carbon / Spectrum / Lucide / Phosphor / storybook-design-token addon).

## §1 · `<FullSwatchTable>` — adoptions and rejections

**Pattern that wins:** Carbon's multi-theme columns. One row per token, columns = swatch + token name + raw value + paired-foreground sample + WCAG ratio + usage notes. Themes are columns, not pages — designers compare across modes constantly.

**Adopt:**
- Multi-theme columns (Carbon) — render all themes simultaneously when ≥3 themes
- **Paired-foreground sample inside the swatch cell** with live WCAG ratio + Pass/Fail AA/AAA badge (Deliveroo + wcag-tokens) — don't make pairing a separate column; embed it
- Single text filter + 4–6 category chips (Primer + Carbon) — never multi-faceted filters; token tables are scanned, not queried
- Per-theme `[data-theme="g90"]` scope wrappers so the same `var(--cds-bg)` resolves differently per column

**Reject:**
- Per-theme pages (forces tab-switching)
- Color-name-as-row-header without a swatch (Tailwind utility-class style — wrong for semantic tokens)
- Separate "accessibility" page (pairing belongs in the main table)
- `storybook-design-token`'s `<DesignTokenDocBlock>` for ≥3 themes — single-theme-only is the dealbreaker

**Performance budget:** target <100ms for 200-token render. Memoize `getComputedStyle(:root)` reads into a `Map`, invalidate only on `[data-theme]` MutationObserver. Don't re-scan per row.

## §2 · `<FullTypeTable>`

**Adopt:** Live pangram sample as widest column (40–50% width). Metadata columns: size (rem + px), line-height (unitless + computed px), weight (numeric + name), letter-spacing (em). Skip font-family when single-family (noise).

**Reject:** Search UI for <20 tokens. A single sortable column suffices.

## §3 · `<FullSpacingTable>`

**Adopt:** Token name + numeric (px + rem) + horizontal bar at actual size + "common usage" caption (Atlassian + Nathan Curtis). Optional second "stack demo" column showing two boxes separated by exact spacing.

**Reject:** Tier-based grouping (element/card/section/modal) as primary structure. Keep tiers as captions only — too prescriptive otherwise.

## §4 · `<FullElevationGrid>`

**Adopt:** Material 3's identical-cards-on-neutral-backdrop pattern. Columns: token name, live card preview, raw `box-shadow` CSS, recommended z-index. Render dark-theme variants in parallel section with dark backdrop (shadows look very different on dark).

**Reject:** Scroll-to-compare demos. Pure-white backdrop. Side-by-side beats sequential for shadow comparison.

## §5 · `<FullIconGrid>`

**Adopt:**
- Sticky search bar at top, prominent
- Phosphor's tag-based fuzzy search (`uFuzzy` or `Fuse.js` — don't write your own)
- Single 24px size in grid; click for detail panel with all sizes/weights/variants
- Hover reveals icon name; click copies token
- Counts visible on category chips
- For variant-heavy sets: segmented control above grid (not multiple icons per cell)

**Reject:** All sizes in grid (visual noise). Category-as-page (forces nav). Modal-only detail (click-to-copy should work from grid).

**Implementation:** use `react-virtuoso` `VirtuosoGrid` for >150 items. Lazy `import.meta.glob`. SVG sprite-sheet alternative for very dense (`<symbol id="...">` + `<use href="#id">`) — one network request.

## §6 · Status state machine for `<StatusPill>` and previews

Original spec uses 4 states: `empty | placeholder | in-progress | filled`. Research recommends **5 + 1 error state**:

| State | Meaning | Visual |
|---|---|---|
| `planned` | MDX exists, no implementation | Dashed-border preview pane, "Not yet authored" text, link to roadmap |
| `in-development` | Implementation exists, no story | Skeleton blocks, "Preview coming soon" |
| `beta` | Renders, may change | Live render + amber banner: "Beta — API may change" |
| `stable` | Production-ready | Live render, no banner |
| `deprecated` | Migrate to alternative | Live render dimmed (60% opacity) + red banner: "Deprecated — use `<X>`" |
| `error` | Runtime failure | Red bordered pane, error icon, "Preview failed" + expandable stack trace |

**Wording**: `Not yet authored` and `In development` read more honestly than `Coming soon` (implies commitment). `Placeholder` is too internal-sounding for public docs. `Beta` over `Experimental` (shorter, more familiar).

**Error boundary**: wrap each preview individually, not the whole page. One broken preview shouldn't kill all of `4-components/`.

## §7 · `<AnatomyDiagram>` — final shape

```tsx
<AnatomyDiagram
  src="/anatomy/modal.svg"        // static SVG with baked-in numbered badges
  alt="Modal anatomy"
  parts={[
    { n: 1, label: "Title", token: "modal.title" },
    { n: 2, label: "Body", token: "modal.body" },
    { n: 3, label: "Close button", token: "modal.close" },
    { n: 4, label: "Footer", token: "modal.footer" },
  ]}
/>
```

**Rules:**
- Static SVG/PNG with baked-in numbered badges (Figma export). Do **not** overlay numbers via absolute positioning on a live render — every reference DS learned this lesson.
- Render legend as `<ol>` to the right (desktop) / beneath (mobile)
- `aria-describedby` linking image to legend list
- Light/dark variants via `<picture>` so screenshots render correctly in both themes
- **Optional**: when SVG is exported with `data-part="N"` attributes, attach `:hover` on legend items to dim non-matching SVG groups. Nice-to-have.

# Appendix C · Auto-generated dashboard patterns

## §1 · Architecture: cache, not live computation

**Decision: stay with the JSON cache pattern (current spec is right).**

- Live MDX computation rejected — would require shipping the entire DS source as data (bundle bloat + private-source leak).
- Server-side aggregation rejected — no server in Storybook pipeline.
- Hybrid (cache + manual refresh button) rejected — refresh button can't run a Node script from the browser without a dev-only websocket (not worth the complexity).

**Three guarantees to add:**
1. CI runs the generator on every PR and commits the JSON
2. Pre-commit hook runs the generator if any tracked source changed
3. `lastGenerated` ISO + git commit SHA in every JSON file, surfaced in the page header

## §2 · Atomic write pattern (failure mode prevention)

```js
// scripts/generate-tracker.mjs
const tmp = `tracker.tmp.${Date.now()}.json`;
await fs.writeFile(tmp, JSON.stringify(payload, null, 2));
await fs.rename(tmp, 'tracker.json');  // atomic on POSIX
```

Prevents half-written JSON from breaking the page mid-generation.

## §3 · Data-freshness UX (anchor to git, not wall-clock)

**Reject:** "5 minutes ago" precision (Sifflet/Metaplane critique — misleading when source changed but cache didn't).

**Adopt:**
- Header chip: `Generated from commit a1b2c3d · 2 days ago`
- Amber banner when `HEAD` differs from generated-at commit: `Source has changed since last regeneration. Run pnpm ds:tracker to refresh.`
- Unit is commits, not time

## §4 · Empty states (PatternFly + Cloudscape pattern)

Three distinct states to handle:

| State | Render |
|---|---|
| **Missing cache** (first run) | `<EmptyState>` with "Tracker hasn't been generated yet" + copyable command. **Don't hide the page** — discoverability matters. |
| **Partial cache** | Render what exists; mark missing sections with muted "Not yet measured" pill. Never fail-render the whole page. |
| **Stale cache** (HEAD ≠ generated-at) | Render data with amber regenerate banner. Don't blank the page. |

## §5 · Severity + finding UX (SonarQube/CodeClimate adoptions)

Five concrete patterns for `<AuditFinding>`:

1. **Severity dot + label** (Critical/High/Medium/Low/Info) — color *plus* shape *plus* text per WCAG
2. **Group by type, sort by severity within group** — readers scan for "what kind" first, "how bad" second
3. **Inline location** — `tokens/color.ts:42` clickable anchor, NOT modal
4. **Per-row action verb** — "Replace `#3366FF` with `color.brand.primary`" beats "Inline value detected"
5. **No dismiss/resolve flow** — these dashboards regenerate; "dismissing" requires state store, out of scope

**Reject:** SonarQube's "quality gate pass/fail" headline. Audit is informational, not blocking. Don't dramatize.

## §6 · Visualization library — don't ship Recharts

Tracker needs:
- 1 horizontal fill bar (overall %)
- ~8 horizontal fill bars (per-section)
- 1 small histogram (severity counts on Audit)

All three are pure CSS — `<div style={{width: '${pct}%'}}>` with two background colors. **Recharts pulls ~90 KB gzipped of D3 submodules into the docs bundle for what amounts to colored rectangles.**

**Recommendation:** small `<FillBar value={0.62} />` component, ~30 lines. If a stacked or grouped bar appears later, evaluate `@nivo/bar` or stick with CSS Grid.

## §7 · Capping + ranking

- "Next N actions" — cap visible at 5, with "Show all" expansion
- Score-then-rank, but expose only order (not raw scores)
- Verb on every row: "Document variant", "Promote to token", "Delete orphan"
- Never passive ("Issue: ...")

## §8 · Schema versioning

```json
{ "schema": 1, "lastGenerated": "...", "commit": "a1b2c3d", ... }
```

MDX checks version, renders graceful error if generator + reader disagree. Critical for safe long-term evolution.

# Appendix D · Storybook 8.4+ / 9 MDX architecture

## §1 · Canonical import pattern — explicit per-file imports

**Storybook 9** moved doc blocks: `@storybook/blocks` → `@storybook/addon-docs/blocks`. (8.4 supports both; 9 only supports new path.)

```mdx
import { Meta, Canvas, Story, Controls } from '@storybook/addon-docs/blocks';
import * as ButtonStories from './Button.stories';
import { PageHeader } from '../_components/page';
```

**Two ways to lower boilerplate cost:**
1. **Barrel re-export** — `_components/index.ts` re-exports all 30 components; each MDX has one line: `import { PageHeader, SourceOfTruthList, ... } from '../_components';`
2. **`<Template />` MDX composition** (Storybook 9) — shared `_templates/ComponentDocsTemplate.mdx` does all imports + layout once; per-page MDX renders `<Template />`

## §2 · Do NOT use `MDXProvider` for global component injection

Storybook officially **deprecated** this path. [Issue #13468](https://github.com/storybookjs/storybook/issues/13468): components passed to `MDXProvider` produce *"Component was not imported"* warnings since 6.1.

**Don't try to skip imports.** TypeScript loses the import graph (no jump-to-definition, broken renames, blind unused-import linters), bundle no longer tree-shakes, future Storybook may break it again.

**Use `parameters.docs.container`** for theme/provider wrapping only. Wrap `DocsContainer` in your own provider — works fine for context, wrong for "don't write `import`".

## §3 · Frontmatter — `export const` is canonical

**Don't enable YAML frontmatter unless a non-Storybook consumer reads the same files.** The canonical pattern:

```mdx
export const frontmatter = {
  status: 'stable',
  category: 'foundations',
  lastUpdated: '2026-05-09',
};
```

**Type frontmatter via `_components/types.ts` + `mdx.d.ts`:**

```ts
// mdx.d.ts
declare module '*.mdx' {
  export const frontmatter: import('./_components/types').PageFrontmatter;
  const Component: React.FC;
  export default Component;
}
```

So `import.meta.glob('./**/*.mdx', { eager: true })` aggregators get typed access.

## §4 · `import.meta.glob` patterns

- `eager: true` — returns `{ '/path/foo.mdx': { default: MDXComponent, frontmatter: {...} } }`. Default = React component; named exports come along.
- `eager: false` — values are `() => Promise<Module>`; await each. Use for index pages listing 15+ docs without bundling all.
- **Glob arguments must be string literals** (no variables) — wrap glob calls in dedicated helpers and re-export.

## §5 · `docs.container` vs `docs.page`

- `parameters.docs.container` — wraps **whole docs route** (provider, theme, layout chrome). Set globally in `preview.ts`.
- `parameters.docs.page` — controls **autodocs body** when no MDX file. Override per-component to swap default `<Title/><Primary/><Controls/><Stories/>` template.

**For our exemplar with hand-authored MDX everywhere, only `docs.container` is needed.**

## §6 · CSS scoping rules

- Global CSS in `preview.ts` (`import './globals.css'`) — loads into iframe, applies to stories + docs. HMR works.
- Component-level `import './style.css'` — also loads into iframe; **not scoped** unless using CSS Modules.
- CSS Modules (`*.module.css`) — fully scoped, work out of the box with Vite.

Storybook 9 has an isolation barrier on by default so docs styles don't leak into embedded `<Canvas>` story frames.

## §7 · Tree-shaking lucide-react

`lucide-react` IS tree-shakable when imported as `import { Star } from 'lucide-react'`. **Pitfalls:**
- Dev bundle ships everything (Vite doesn't tree-shake in dev — Rollup does in production). Surprising on Chromatic snapshot startup.
- **Barrel files defeat tree-shaking** when re-exports include side effects. Mark the package `"sideEffects": false` in `package.json` so Rollup can drop unused re-exports.
- Verify with `vite build` + `rollup-plugin-visualizer`.

## §8 · Hot-reload behavior

- Component .tsx changes → MDX pages consuming them HMR cleanly
- `main.js`/`preview.js` edits → full reload, providers reset ([Issue #9192](https://github.com/storybookjs/storybook/issues/9192))
- Iframe boundary: docs render in preview iframe; manager UI is separate React tree. Wrap risky components in error boundaries — crashes in iframe surface as empty docs panel, not sidebar error.

# Appendix E · Architectural risks and refactor recommendations

From the architecture review. Top 5 refactors, impact-ordered:

## §1 · Pin schemas before Phase 1 (highest leverage, lowest cost)

**Add a Phase 0:**
- `schemas/manifest.schema.json`
- `schemas/components-index.schema.json`
- `schemas/frontmatter.schema.json`

Generate TypeScript types from them via `json-schema-to-typescript`. Every component consumes the type. **Result:** typo in manifest becomes a compile error, not a silent runtime break across 5 components.

## §2 · Split human and machine writes on the manifest

**Problem (current spec):** `index-manifest.json` has both team-authored fields (`display_name`, `lede`, `rules`) AND machine-mutated fields (`counts`, `last_filled_at`). First time `evolve` runs after a hand edit, you'll either clobber the edit or merge incorrectly.

**Fix — option A:** namespace the machine fields under `_computed` that humans agree never to touch:

```json
{
  "display_name": "shadcn/ui exemplar",
  "lede": "...",
  "_computed": {
    "counts": {...},
    "last_filled_at": "..."
  }
}
```

**Fix — option B:** split into two files:
- `index-manifest.json` (human)
- `index-manifest.computed.json` (machine, `.gitignore`'d optionally)

Option A is simpler; option B is cleaner for git diff hygiene.

## §3 · Introduce `<Icon name>` indirection (resolves Decision #8)

**Problem:** lucide-react hardcoded across 10+ components. Swapping libraries (Material's `<md-icon>`, Fluent's `@fluentui/react-icons`, Phosphor's `@phosphor-icons/react`) means 10+ rewrites.

**Fix:** single L1 component reads from an `IconLibraryAdapter` injected at the harness root:

```tsx
// adapters/lucide.tsx
export const lucideAdapter: IconLibraryAdapter = {
  resolve: (name) => LUCIDE_MAP[name] ?? FileText,
  render: (Component, props) => <Component size={props.size} {...props} />,
};

// _components/Icon.tsx
export function Icon({ name, ...props }: IconProps) {
  const adapter = useIconAdapter();  // from context
  return adapter.render(adapter.resolve(name), props);
}
```

Every other component uses `<Icon name="check-circle">`, never imports lucide directly.

## §4 · Collapse Mini/Full into a `<TokenPreview>` chassis

**Problem:** 10 components doing 5 jobs. `<MiniSwatchRow>` + `<FullSwatchTable>` share 80% of the logic (token discovery, theme awareness, hex rendering).

**Fix:** `<TokenPreview type="color|type|spacing|elevation|icons" size="mini|full" filterable searchable />`. Five components, one prop signature, one `useTokens()` hook. **Result:** ~40% fewer components to maintain, no chance of Mini and Full diverging on what counts as a token.

**Lesser refactor (if full collapse is too clever):** at minimum a shared `useTokens(type)` hook so token discovery only lives in one place. Today, ten components duplicate `getComputedStyle(:root)` enumeration — if the source changes (CSS layers, `@property`, theme variants), you have ten edits.

## §5 · Move tracker computation to regeneration time

**Problem:** `<TrackerPage>` "computed at render time". At 1000 components that's an O(n log n) sort on every page mount.

**Fix:** mirror Audit's pattern — `tracker.json` cache filled by `scripts/generate-tracker.mjs`, rendered by dumb display components. Architecture becomes symmetric (Tracker + Audit both cache-driven), gives 1000-component scale headroom.

## §6 · Three risks the spec doesn't currently mitigate

1. **MDX/JSON drift across `evolve` runs** — no transactional contract, no schema validation, no test that round-trips an `evolve` over a manually-edited manifest and confirms hand edits survive. **Mitigation:** add a contract test in CI. Every `evolve` must preserve every team-authored field byte-for-byte.

2. **Browser-API dependence with no client/server boundary** — `getComputedStyle`, `import.meta.glob`, iframe Figma embeds all assume browser. Storybook 7+ server rendering will break these silently. **Mitigation:** wrap browser-API consumers in `<ClientOnly>` wrapper with skeleton fallback for SSR pass.

3. **Versioning & upgrade story** — once teams adopt v1 of these 30 components in their repos, how do you ship v2? The spec describes `establish (re-run)` as offering a diff prompt, but says nothing about template version pinning, breaking changes, or migration scripts. **Mitigation:** add a `template_version: "1.0"` field to `index-manifest.json`. Subsequent template releases ship migration scripts (`migrate-1-to-2.mjs`). Document compatibility matrix.

## §7 · Coupling map (for change-impact estimation)

| Change | Blast radius |
|---|---|
| `index-manifest.json` shape | ~15 components — **god-object risk** |
| Swap icon library | ~10 components — **fixable with adapter (§3)** |
| Change `Status` enum | ~7 components + every MDX `frontmatter.status` — **fixable with schema (§1)** |
| Change CSS variable naming | All Mini/Full token visualizations — **fixable with shared hook (§4)** |
| Add new page type | New section + new MDX skeleton + new IA folder — **expected** |

## §8 · Missing concerns (none in spec; surface for v2)

- Theme system beyond light/dark (brand themes, density modes, high-contrast)
- i18n (all copy hardcoded English)
- RTL (every visual sketch is LTR)
- Performance budgets (`<FullIconGrid>` enumerates 1000+ Lucide icons × 5 sizes = 5000 DOM nodes; no virtualization spec)
- Bundle splitting (welcome MDX may import all 30 components today)
- Accessibility of harness components themselves (`<FillRatioBar>` has no `role="progressbar"` spec)
- Test contract (zero mention of tests)
- Error boundaries

### The single biggest gap (visual design quality)

> "Beautiful Defaults: carefully chosen default styles, so you get great design out-of-the-box."

# Appendix G · Visual design + shadcn + a11y / perf / themes / versioning

## §1 · Visual design quality (the print-quality gap)

### The 8 typography ratios to memorize

Pulled from PLUS-BS4 source + Carbon + Primer token files (not estimates):

1. **Hero H1 = 56px / 700 / lh 1.1 / letter-spacing -0.02em / max-width 780px** (PLUS `index.html:55–61`)
2. **Section H2 below display drops to 24–32px**, letter-spacing 0 — never carry display tracking down
3. **Body line-height 1.5 minimum**, lede line-height 1.5–1.625 (loosens slightly so it reads as "hero copy")
4. **Eyebrow letter-spacing 0.10–0.12em uppercase** at **11–12px / 600** — Carbon and PLUS converge here
5. Lato-style display fonts: **weight 700 with negative tracking**; IBM Plex display: **weight 300 with zero tracking** — inverse strategies, both polished. Pick one and commit.
6. Card title H3: **22px / 700**, paragraph below: **14px / 1.45–1.5 lh** in `on-surface-variant` (~70% black) — never full black
7. Code chip: always `font-size: 0.75em` (not absolute) so it shrinks proportionally inside any heading
8. Path/breadcrumb mono text in cards: **11px** in primary color — tiny accent that says "this links to a real file"

### The 7 spacing rhythm rules

- **Section margin-bottom: 56px** (PLUS) to **64–80px** (Carbon `--cds-spacing-09: 3rem` + `spacing-10: 4rem`). Current shadcn page sits at ~32px.
- **Hero padding: 56px × 48px**. Anything ≤24px is a banner, not a hero.
- **Three radius tiers**: hero 24px / section card 16px / chip 12px or 999px. Never mix five.
- **Section header bottom-rule pattern**: 12px padding-bottom + 1px outline-variant border-bottom + 24px margin-bottom
- **Card grid gap: 24px** for hero/feature cards (2-col), **16px** for doc cards (3-col). Bigger cards → bigger gutters.
- **Card padding: 24–28px** for feature cards, **20–22px** for doc cards. Anything ≤16px reads as "list item with border."
- **Container max-width 1280px with 32px outer padding**, prose max-width 640–720px (40–45rem) — never let body run full container width

### Color use beyond tokens (4 specific moves)

1. **Hero card uses solid primary**, not tinted neutral. `background: var(--color-primary)` with `color: var(--color-on-primary)` and a radial gradient glow (`radial-gradient(circle at center, rgba(255,255,255,0.18), transparent 60%)`) tucked into the top-right corner.
2. **Sections revert to surface-container-lowest (white)** — the contrast between solid hero and white body is the rhythm. Don't tint section backgrounds.
3. **Brand color appears in exactly 4 places**: hero, kicker/eyebrows, counter circles (in 8% tint bg + primary text), monospace path text. Four small repetitions, not one giant swatch grid.
4. **Hairline rule color** is `--color-outline-variant` (warm neutral) at 1px — never `#e5e7eb` Tailwind default. The slightly-tinted hairline reads as "designed."

### Hover/focus recipes (verbatim from PLUS)

```css
/* Feature card hover (big card) */
transition: transform 120ms ease, box-shadow 120ms ease, border-color 120ms ease;
:hover {
  transform: translateY(-2px);
  box-shadow: var(--elevation-light-3);
  border-color: var(--color-primary-container);
}

/* Doc card hover (small card, gentler) */
transition: border-color 120ms ease, transform 120ms ease;
:hover {
  border-color: var(--color-primary-container);
  transform: translateY(-1px);
  /* no shadow change — too noisy at small sizes */
}
```

**120ms ease** is the universal default (PLUS, Carbon, Primer). 200ms feels sluggish; 80ms feels twitchy. Border color on hover transitions to `primary-container` (lighter primary tint), not full primary.

### The "designed surface" primitives

- **Hairline rule under every section header** — single highest-leverage chrome decision
- **Eyebrow above titles, not inside them** — separate 11–12px uppercase line with 8px margin-bottom *above* the H1. Eyebrow tells category; H1 tells subject.
- **Numbered counter circles**: 22px circle, primary-state-08 bg, brand primary 11px/700 text, 32px left padding. For non-negotiable rules / principle lists.
- **Tonal layered surfaces**: 4-step neutral stack — `surface-container-lowest` (white page) → `surface` (card) → `surface-container-low` (preview area) → `surface-container` (chip bg). Two-tier (white + slate-50) is why everything feels flat.
- **Hero corner glow**: 480×480 radial gradient at 18% white opacity, positioned `inset: -40% -20% auto auto`, fading at 60%. Reads as "designed hero" vs "blue rectangle."
- **Stat-pair pattern** in hero metadata: 11px uppercase label `display: block` + 13px value below, gap 32px.
- **Right-rail TOC**: 13px / lh 1.5 / on-surface-variant color, 2px-wide left bar in primary-state-08 marking active section, ~240px column width.
- **Sidebar grouping**: 11–12px uppercase on-surface-variant group label, 4px gap to first item, **24–32px gap between groups**.

### The print-quality summary, in one paragraph

A docs page reads as **printed** when (a) it has **three type sizes** simultaneously visible (display, body, eyebrow) with measurably different leading, (b) sections are **separated by a hairline plus 56–80px**, not by a tinted background, (c) **negative letter-spacing on display + positive on eyebrow** creates visible micro-tension, (d) the **container is capped at 1184–1280px** with body prose further capped at 640–720px so lines don't run, (e) **hover transitions are 120ms** and move things by **1–2px max**, (f) **brand color appears in the hero, in eyebrows, in counter circles, and in monospace path text** — four small repetitions, not one giant swatch grid, and (g) every numeric value comes from a **token, not a literal** — chip radius (12px), card radius (16px), hero radius (24px) all multiples of 4 from a shared scale.

The shadcn welcome failure mode is usually one or two of these missing — most often (a) eyebrow absent, (b) sections at 32px instead of 56–80px, (c) brand color demoted to swatch, and (g) ad-hoc radii and paddings that don't ladder.

## §2 · Performance budgets

### Concrete numbers

- **lucide-react per-icon import**: ~0.5–1 KB raw, ~0.3 KB gzipped. 50 icons = ~25 KB raw / ~8 KB gzipped. Full library is ~1.8 MB — `import * as Icons` is catastrophic.
- **Storybook 6.4+ on-demand baseline**: manager bundle ~3 MB, preview ~5 MB pre-tree-shake. Cold load LCP for a single page realistically ~1.5–2.5s on broadband, ~4–6s on slow 3G.
- **`<FullIconGrid>` real-world cost**: 1000 icons × 5 sizes = 5000 SVGs × 10–20 DOM nodes = **50k–100k DOM nodes**. Chrome chokes >32k. **Virtualization mandatory at >500 items.**

### Recommended budgets for the exemplar

```
Per docs page (welcome, foundation, style, etc.):
  - JS transferred:    < 200 KB gzipped
  - LCP:               < 2.0s broadband, < 4.0s slow 3G
  - INP:               < 100 ms
  - DOM nodes:         < 3000

Special pages (FullIconGrid, FullSwatchTable with N themes):
  - JS transferred:    < 350 KB gzipped
  - DOM nodes:         < 5000 (virtualization at >500 items)
  - LCP:               < 3.0s

Tracker / Audit:
  - Pre-baked JSON, not live computation. < 50 KB JSON payload.
```

### 5 splitting strategies

1. **Trust Storybook 6.4+ on-demand**. Don't roll custom code-splitting. Verify with `storybook build --stats-json` + bundle analyzer.
2. **Per-icon imports only**. Lint rule banning `import { … } from 'lucide-react'` barrels in components rendered at scale.
3. **Virtualize at >500 items**. `<FullIconGrid>`, `<FullSwatchTable>` with very large token sets — wrap in `react-virtuoso` Grid.
4. **Pre-bake Tracker/Audit JSON at build time** (confirmed in round 1).
5. **Lazy-load heavy deps** (Recharts) via `React.lazy()` per page so Foundation pages don't pay for data-viz imports.

## §3 · Accessibility per component (concrete ARIA contracts)

### Per-component pattern table

| Component | Pattern | Concrete prescription |
|---|---|---|
| `<FillRatioBar>` | Determinate progressbar | `role="progressbar"`, `aria-valuemin="0" aria-valuemax="100" aria-valuenow={pct}`, `aria-valuetext="42 of 50 components stable (84%)"` so SR users hear the count, not just the percent |
| `<StatusPill>` | Decorative text | NOT `role="status"` (live region — fires on every render). Plain text + `aria-label` if icon-only. For dynamic Tracker freshness, wrap *container* in `role="status" aria-live="polite"` |
| `<PageCard>` (clickable) | One primary `<a>`, full-card hit area via pseudo-element | NOT card-wrapping `<a>` (kills nested links + announces full subtree as ~25s read string). Use `<article>` with inner `<h3><a>...</a></h3>` whose `::after` covers the card. Secondary actions sit *above* via `position: relative; z-index: 1` |
| `<PageCardGrid>` | Landmark + heading-organized list | `<section aria-labelledby="...">` containing `<ul role="list">` of cards. Don't roving-tabindex — these aren't a composite widget |
| `<FullSwatchTable>` | Native `<table>` with `<caption>` + `<th scope>` | `<caption>` = "Color tokens, all 4 themes". `<th scope="row">` for token names, `<th scope="col">` for theme columns. NEVER `role="grid"` — that turns rows into a 2-D widget |
| `<FullIconGrid>` | `role="list"` + searchable label per icon | Each icon: `<li><button aria-label="copy icon name">`. Don't use `<img>` for inline SVGs — use `aria-hidden="true"` on the `<svg>` |
| `<AuditFinding>` | List item with heading + region | `<li>` inside `<ul>`. Inside: `<h4>` for finding name + `<p>` for diagnosis. If grouped by severity, wrap each bucket in `<section aria-labelledby="audit-blockers-h">` |
| `<AnatomyDiagram>` | `<figure>` with image + numbered legend `<ol>` referenced by `aria-describedby` | Numbered SVG badges = pure decoration (`aria-hidden`); semantics live in the `<ol>` |
| `<RulesPanel>` counter circles | Pure CSS pseudo-element | Number is decorative — rule text carries meaning. Use `::before { content: counter(rules) }`. Zero ARIA needed. |
| `<PageHeader>` | Landmark + heading hierarchy | `<header>` containing `<h1>`, link cluster, lede. Source/Related as `<nav aria-label="Page references">` |

### Cross-cutting WCAG 2.1 AA concerns

1. **Contrast for status pills**. The "in-progress" amber is highest-risk — most amber-on-white pills score ~3.2:1. Mitigation: darken amber text or restrict to ≥18pt. **Test all 5 pill states across all themes** (4 themes × 5 states = 20 contrast checks; bake into `tokens.css` validation).
2. **Focus rings on cards**. Default `outline` is killed by most CSS resets; reinstate with `:focus-visible` + 2px outline using `--color-focus-ring` token. Test against every theme — Carbon's g100 needs different ring color than white.
3. **Lighthouse parity**: Carbon, Fluent, M3 docs all score 92–98 on Lighthouse a11y. Failing 2–8 points are almost always (a) low-contrast inactive states and (b) missing `<caption>` on token tables. Easy wins.

## §4 · Theme system architecture (multi-axis)

### Canonical pattern: stack `data-*` attributes

```css
/* tokens.css — one file, scoped by data attributes */
:root[data-theme="white"] { --color-background: #fff; --color-text: #161616; }
:root[data-theme="g10"]   { --color-background: #f4f4f4; --color-text: #161616; }
:root[data-theme="g90"]   { --color-background: #262626; --color-text: #f4f4f4; }
:root[data-theme="g100"]  { --color-background: #161616; --color-text: #f4f4f4; }

:root[data-density="comfortable"] { --component-height: 48px; --row-padding: 12px; }
:root[data-density="compact"]     { --component-height: 32px; --row-padding: 4px; }

:root[data-contrast="high"] { --color-border: CanvasText; }
:root[data-brand="acme"]    { --color-brand: #ff0066; }
```

Components reference only the **alias** (`--component-height`); they never know about themes. `--space-4` stays constant; density-sensitive components use `--component-height` and `--row-padding` instead.

### Manifest shape

```json
{
  "axes": {
    "theme":    { "options": ["white", "g10", "g90", "g100"], "default": "white" },
    "density":  { "options": ["comfortable", "compact"],      "default": "comfortable" },
    "contrast": { "options": ["normal", "high"],              "default": "normal" },
    "brand":    { "options": ["default", "acme", "globex"],   "default": "default" }
  }
}
```

The manifest declares **axes**, not a flat theme list — scales to N brands × M densities without quadratic blowup.

### Storybook integration

```js
// .storybook/preview.ts
export const globalTypes = {
  theme:    { defaultValue: 'white',       toolbar: { items: ['white','g10','g90','g100'] } },
  density:  { defaultValue: 'comfortable', toolbar: { items: ['comfortable','compact'] } },
  contrast: { defaultValue: 'normal',      toolbar: { items: ['normal','high'] } },
};
export const decorators = [(Story, ctx) => {
  const root = document.documentElement;
  root.dataset.theme    = ctx.globals.theme;
  root.dataset.density  = ctx.globals.density;
  root.dataset.contrast = ctx.globals.contrast;
  return Story();
}];
```

### `<FullSwatchTable>` rendering with multi-theme

With the data-attribute architecture, multi-theme columns become N CSS-isolated wrappers each with `data-theme="..."` — no JS, no React context juggling.

## §5 · Versioning and upgrade story

### Two version fields, not one

- `template_version` in manifest — the **contract** version (bumps on breaking API changes to components like `<PageHeader>`)
- `_generator_version` per MDX file — version of `/hd:setup` or `evolve` that wrote it (lets us detect mixed-version repos)

### Semver on the contract

`template_version: "2.0.0"` triggers:
- `MIGRATION-v1-to-v2.md` doc shipped in the skill's `references/`
- Codemod script in `scripts/migrate-v1-to-v2.{ts,sh}` rewriting MDX import sites + prop names
- Console warnings on v1 components for one minor version before removal

### Diff-on-update via `/hd:maintain --check-updates`

Mirrors `shadcn diff` exactly:

```
hd-maintain detects template_version: 1.x in repo
Latest is 2.0. Breaking changes:
  - <PageHeader> renamed `title` → `heading`
  - <StatusPill> added required `label` prop
Run codemod? [y/N]  → invokes scripts/migrate-v1-to-v2.ts
```

### Compatibility matrix in README

```
| template_version | Storybook | React | Lucide |
|---|---|---|---|
| 1.x              | 7.x–8.x   | 18    | 0.4xx  |
| 2.x              | 8.x+      | 19    | 0.5xx  |
```

### Deprecation policy

Each `template_version: N` is supported until `N+2` ships (~2 majors / minimum 6 months). Deprecated components log a one-time `console.warn` in dev with link to migration doc.

### MDX safety net — adapter components

For highest-churn primitives (`<PageHeader>`, `<StatusPill>`), ship thin adapter under `components/v1/` for one major after a breaking change. Mirrors MUI's `adaptV4Theme`.

### YAGNI gate

Don't build the codemod runner until v2 actually ships. For v1, upgrade story is "here's the diff, hand-edit". Codemod tooling is Phase-2 once we know which props churn.
